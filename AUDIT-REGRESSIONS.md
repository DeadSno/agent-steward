## 1. Детали (D-01 … D-17)

Для каждого пункта: что сломано, где в коде, последствия, подтверждено ли чтением кода.

### D-01. ps-wrapper: потеря живого стриминга лога (регрессия)
- **Файл:** `src/core/ps-wrapper.ts`, функция `Invoke-OpenCodeOnce`, строки ~309–329.
- **Было:** `& opencode *>&1 | ForEach { Format-LogLine } | Out-File -Append` — строки пишутся в лог по мере поступления.
- **Стало:** `$output = & … *>&1` — весь вывод буферизируется в переменную до завершения процесса, и только потом один раз пишется в лог через `Out-File -Append` (строки 313, 317).
- **Последствия:**
  - `get_task_logs` / дашборд слепы во время выполнения (runs длятся часами).
  - Расход RAM на длинных verbose-задачах (весь вывод в памяти).
  - При убийстве самой обёртки лог не записывается вообще (буфер не сбрасывается).
- **Причина изменения:** неочевидна; `$LASTEXITCODE` после пайплайна и так корректен.
- **Подтверждено в коде:** да.

### D-02. Telegram: чанкинг после форматирования (риск 400 «can't parse entities»)
- **Файл:** `src/core/telegram.ts`.
- **Проблема:** `sendTelegramMessage` вызывает `formatTelegramText(text)` → получает уже экранированный HTML/MarkdownV2, а затем `splitTelegramMessage(formatted)` режет готовое сообщение по 4096 (строки 207–220). Тег `<a href=…>` или `*bold*` может разорваться между чанками → Telegram отвечает 400 «can't parse entities» → уведомление теряется.
- **Защита:** есть только от surrogate pair и `\` (строки 162–168), но сущности не спасает.
- **Подтверждено в коде:** да.

### D-03. Race при снятии stale-lock (обе платформы)
- **Файлы:** `src/core/ps-wrapper.ts` (строки 153–165, `Remove-Item` → `CreateNew`), `src/core/lock.ts` (POSIX, `fs.rm`, строка 51).
- **Проблема:** если два воркера одновременно видят мёртвый PID, второй может удалить свежий lock первого между `mkdir` и своим `rm` → оба считают, что владеют lock → двойной запуск.
- **Фикс:** атомарный rename (`.d` → `.d.stale-$$` / `Move-Item` в `.stale-<pid>`) вместо `remove`, затем create; не удалось rename — уже перехватили, пропуск.
- **Подтверждено в коде:** частично — Windows-side в ps-wrapper есть `Remove-Item` (строка 154); POSIX-side в lock.ts использует `fs.rm` без атомарного rename.

### D-04. Лимит имени задачи не учитывает профиль
- **Файл:** `src/types.ts`, функция `validateTaskName`, строка 93 (`MAX_TASK_NAME_LENGTH = 209`).
- **Проблема:** 209 рассчитано под префикс `\OpenCode\windows-scheduler\` (28 симв.). У не-default профиля папка `windows-scheduler-<profile>` (до ~58 симв.) → 209 + префикс > 237 лимита schtasks. Валидация пропускает, `/create` падает.
- **Фикс:** считать лимит от фактической длины `TASK_FOLDER_NAME.length`.
- **Подтверждено в коде:** да (строки 16–19, 91–99).

### D-05. deleteProfile не снимает задачи ОС (+ миграционный край)
- **Файл:** `src/profiles.ts`, функция `deleteProfile`, строки 202–217.
- **Проблема:** директория профиля удаляется, но его блок crontab / папка Планировщика остаются → задачи продолжают запускаться из удалённых обёрток (ошибки/сироты).
- **Миграционный край:** задачи не-default профилей, созданные до per-profile папок, лежат в общей default-папке — после апгрейда осиротеют.
- **Фикс:** uninstall задач профиля при удалении + разовая миграция/чистка.
- **Подтверждено в коде:** да — `deleteProfile` только `fs.rmSync(dir)` (строка 209), нет вызова scheduler backend.

### D-06. Локали DE/FR/ES/IT/PL: декодирование консоли всё ещё CP866
- **Файл:** `src/core/scheduler/windows.ts`, функция `decodeConsoleOutput`, строки 32–43.
- **Проблема:** фоллбек только на CP866. На немецкой/французской/польской Windows OEM-кодировка 850/852/1252 → акцентные ключи (`nächste ausführungszeit`, `última ejecución`, `modalità di accesso`, `następne uruchomienie`) превращаются в кракозябры и не матчатся. ASCII-ключи (taskName/status) работают, а `nextRun`/`logonMode`/`lastResult` на этих локалях остаются null.
- **Фикс:** определять OEMCP (реестр `Nls\CodePage` / `GetOEMCP`) или перейти на `schtasks /query /fo CSV /v /nh` с позиционным разбором — локале-независимо.
- **Подтверждено в коде:** да (строки 32–43, только cp866).

### D-07. sleep().unref() в telegram-retry
- **Файл:** `src/core/telegram.ts`, функция `sleep` (строки 177–183), 429-ретрай (строки 251–258).
- **Проблема:** `record-history` — короткоживущий процесс; `unref`-таймер во время 429-паузы не держит event loop → процесс может завершиться до повторной отправки → уведомление теряется.
- **Фикс:** на время retry держать timer ref-нутым.
- **Подтверждено в коде:** да (`timer.unref?.()` строка 181).

### D-08. POSIX-рекордер передаёт "-" "-" вместо токенов/стоимости (старое, остаточное)
- **Файл:** `src/core/record-history.ts` (и `ps-wrapper.ts` `Get-UsageFromLog`, строки 418–483).
- **Проблема:** Windows парсит usage из лога, bash/POSIX — нет → аналитика на Linux/macOS пустая.
- **Фикс:** парсинг лога перенести в `record-history.ts` (получит лог сам, обе платформы выиграют автоматически).
- **Подтверждено в коде:** частично — `Get-UsageFromLog` есть только в ps-wrapper.

### D-09. Промпт через argv на POSIX (старое, остаточное)
- **Проблема:** на Windows есть backstop ≤30000 символов; на POSIX промпт через argv остался без кроссплатформенной валидации размера или stdin.
- **Фикс:** кроссплатформенная валидация размера или stdin.

### D-10. run_with_timeout убивает только прямого ребёнка (старое, остаточное)
- **Проблема:** убивает `bash -c`, внуки (`npm test` и его дети) переживают таймаут.
- **Фикс:** `setsid` / `pkill -P` или `exec` для одиночных команд.

### D-11. GitHub-совместимые хуки: legacy tolerance=0, без replay-защиты (старое, остаточное)
- **Проблема:** token-only режим тоже replayable. Нужно задокументировать guidance по отправителям.

### D-12. Карантин секретов: side-effect при чтении, не восстанавливает автоматически (старое, остаточное)
- **Проблема:** срабатывает на чтении и не восстанавливает данные автоматически.
- **Фикс:** описать recovery из `.corrupt-*` в FAQ.

### D-13. README: нет quickstart + неточности формулировок (старое, остаточное)
- **Визуал на месте:** бейджи присутствуют (README строки 5–9), файл `docs/dashboard.png` существует и встроен (строка 27) — скриншот и бейджи не нуждаются в добавлении.
- **Отсутствует:** quickstart — короткий сценарий «install → первая задача одним вызовом → дашборд» в начале README.
- **Точность формулировок:** клейм «мгновенный EN дашборда» неточен при русских литералах клиента (это в бэклоге) — смягчить wording; совет `npm install -g` без поля `bin` в package.json — лишний, проверить и убрать при отсутствии bin.

### D-14. CI: node матрица [22, 24] тестирует последний 22.x, а не заявленный 22.22+ (старое, остаточное)
- **Файл:** `.github/workflows/ci.yml`, строка 22 (`node: [22, 24]`).
- **Фикс:** запинить `22.22.0` в матрицу.

### D-15. main отстаёт (старое, остаточное)
- **Фикс:** смержить dev→main, тэг v1.5.5, публикация через workflow (проверка version==tag уже есть); NPM_TOKEN → OIDC до янв 2027 (отмечено как отдельная задача в аудите).

### D-16. e2e-стаб только Windows (opencode.cmd) (старое, остаточное)
