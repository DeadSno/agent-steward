# План тестирования плагина `agent-steward` (plugin id `opencode-windows-scheduler`)

**Версия плагина:** 0.0.8 · **Платформа прогона:** Windows 11 · **Дата:** 25.11.2026  
**Объект:** весь плагин — ядро, MCP-инструменты, GUI OpenCode, веб-дашборд, TUI, БД, интеграции, локальный ассистент триажа, самодиагностика, DLQ, durable-запуски, pipeline-as-code.  
**Цель:** доказать три свойства для каждой детали:

1. подсистема работает (функционально и на ошибках);
2. у агента есть доступ к подсистеме (MCP-инструмент или документированный обходной путь);
3. пользователь может сделать то же самое через GUI/дашборд/TUI, а результат совпадает.

> **100% покрытие:** каждая деталь (D01–D18) содержит не только «счастливый путь», но и ошибки, граничные значения, узкие места, планы улучшений и доработки. Подзадачи с префиксом `Sxx.BP.*` — это проверка «узких мест / багов / улучшений / доработок» и обязательны для приёмки детали.

## 0. Как пользоваться планом

### 0.1 Уровни декомпозиции

| Уровень | Обозначение | Что это |
|---|---|---|
| Деталь | `D01…D18` | Крупная подсистема плагина |
| Задача | `T01.1` | Проверяемая функция внутри детали |
| Подзадача | `S01.1.1` | Один конкретный шаг с ожидаемым результатом |
| Узкое место / баг / улучшение | `Sxx.BP.y` | Проверка слабого места, дефекта или плана улучшения |

Каждая подзадача — чекбокс. Деталь считается принятой, когда закрыты **все** её подзадачи (включая `Sxx.BP.*`) и выполнены три критерия из шапки детали.

### 0.3 Подготовка окружения

```powershell
# Выполнять из корня чек-аута agent-steward (например, .steward-dev или tp-audit-dev)
npm run build          # tsc: dist/ (сервер, RPC, ядро)
npm run build:gui      # vite: gui-experimental.cjs (панель OpenCode)
npm test               # 140 файлов test-*.mjs (130 npm-скриптов), полный регресс
node scripts/demo-dashboard.mjs --port 3782   # демо-дашборд с сид-данными
```

- Текущая схема БД: `SCHEMA_VERSION = 14` (таблицы обратной связи `feedback_outbox`/`feedback_spam`; миграция с legacy-БД 10 → 14 описана в S15.1.2).
- GUI: OpenCode → боковая панель «Планировщик Windows». После пересборки панель перезагрузить.
- MCP: 34 инструмента доступны агенту после подключения плагина. Каталог Code Mode раннера показывает только 8 (`schedule_task`, `update_task`, `list_tasks`, `run_task_now`, `get_history`, `get_task_logs`, `dry_run`, `get_dashboard_info`); остальные вызываются по имени через MCP/CLI/HTTP RPC — ограничение моста, а не реестра (QA-D316-19).
- Дашборд: `http://127.0.0.1:3782/` (порт может отличаться, смотреть `get_dashboard_info`).
- Логи прогона: вывод `npm test` (при необходимости перенаправить в `test-run.log`); артефакты GUI — `gui-experimental.cjs` (создаётся `npm run build:gui`).
- Актуальная ветка плана: `dev` (34 инструмента, 130 npm-скриптов). Legacy-чек-аут `steward-work` содержит 30 инструментов и 113 npm-скриптов — его счётчики здесь не используются.

## 2. Детали, задачи, подзадачи

### D01. Ядро расписаний и ОС-бэкенды

**Критерии приёмки:** cron-выражения и окна считаются верно; задачи реально создаются в планировщике ОС; на Windows/macOS/Linux используется свой бэкенд; one-shot срабатывает один раз.  
**Доступ агента:** `schedule_task`, `update_task`, `dry_run` (поля `schedule`, `timezone`, `activeDays`, `notBefore/notAfter`, `windowPolicy`, `runAt`, `triggerType`).  
**Доступ пользователя:** GUI-форма (пресеты, cron, дни недели, окно, timezone), дашборд (отображение nextRun).

#### T01.1. Разбор cron и расчёт next/prev

| ID | Подзадача | Шаги | Ожидаемый результат |
|---|---|---|---|
| S01.1.1 | 🧪 Валидный cron | `parseCron("*/5 * * * *")`, `nextRun` | Следующий запуск ≤ 5 минут от «сейчас» |
| S01.1.2 | 🧪 Невалидный cron | `parseCron("61 * * * *")` | Понятная ошибка, задача не создаётся |
| S01.1.3 | 🧪 Timezone | задача с `timezone: "Europe/Moscow"` | nextRun пересчитан в UTC корректно (разница 3 ч) |
| S01.1.4 | 🧪 Дни недели | `activeDays: [1,2,3,4,5]` | Суббота/воскресенье пропускаются |
| S01.1.5 | 🧪 Окно `notBefore/notAfter` + `skip/postpone/run` | задача «каждые 30 мин, 09:00–18:00» | `skip` не запускает вне окна, `postpone` переносит на границу, `run` игнорирует окно |
| S01.1.6 | 🧪 Пресеты GUI | 5 пресетов из формы | Каждый даёт валидный cron, отображается по-русски |
| S01.1.BP.2 | 🧪 Улучшение: валидация пересечения `activeDays` и окна | `activeDays: [6]` + окно 09:00–18:00 | Если окно никогда не открывается в эти дни — понятное предупреждение при создании |
| S01.1.BP.3 | 🧪 Баг: `nextRun` после перехода на летнее/зимнее время | сменить TZ системы на Europe/Moscow, пересчитать | nextRun сдвигается корректно, нет «застрявших» на 2:00–3:00 |

#### T01.2. Windows-бэкенд (schtasks)

| ID | Подзадача | Шаги | Ожидаемый результат |
|---|---|---|---|

| S01.2.2 | 🤖 Пауза/возобновление | `pause_task` → `resume_task` | Статус в `list_tasks` меняется `paused ↔ active` |
| S01.2.3 | 🤖 Удаление | `delete_task` | Задачи нет ни в `list_tasks`, ни в `schtasks /Query` |
| S01.2.4 | 🧪 Спецсимволы | имя с пробелом, кавычкой и `&`; промпт с кавычками, `&`, кириллицей | Имя с пробелом и кириллицей создаётся; кавычка и `&` отклоняются до записи в БД с понятной ошибкой; спецсимволы промпта сохраняются без искажений |
| S01.2.5 | 🧪 Ошибка прав | запуск без нужных прав | Возвращается читаемая ошибка, БД не засоряется «фантомной» задачей |
| S01.2.BP.1 | 🧪 Узкое место: «тихий успех» schtasks при неверном имени | создать задачу с именем из 255+ знаков | `schtasks` не ругается, но задача не отображается; плагин должен валидировать длину до записи |
| S01.2.BP.2 | 🧪 Улучшение: повторная попытка создания при блокировке schtasks | эмуляция занятой очереди schtasks | Повтор с бэкоффом, не более 3 попыток, потом понятная ошибка |

### D02. Жизненный цикл задач (CRUD)

**Критерии приёмки:** создание/чтение/обновление/удаление и пауза работают из всех интерфейсов; частичное обновление не затирает поля; удаление матрицы каскадное; все мутации попадают в аудит.  
**Доступ агента:** `schedule_task`, `schedule_advanced`, `list_tasks`, `update_task`, `update_advanced`, `delete_task`, `pause_task`, `resume_task`.  
**Доступ пользователя:** GUI-таблица, форма создания/редактирования, кнопки строки; дашборд (запуск/удаление/сухой прогон).

| S02.1.1 | 🤖 Создание минимума | `schedule_task` только `name/schedule/prompt` | Задача создана, cwd = текущий проект |

### E2E-4. Паритет трёх интерфейсов

1. Создать задачу в GUI.
2. Изменить `prompt` агентом (`update_task`).
3. Запустить из дашборда.
4. Прочитать историю агентом.
5. Удалить агентом.

Ожидаемо: на каждом шаге состояние совпадает во всех интерфейсах, аудит содержит `gui → mcp → http → mcp`.

### E2E-5. Матрица

### E2E-6. Уведомления и дайджест

### E2E-7. Секреты и workspace

Добавить `API_KEY` → workspace env `${secret:API_KEY}` → запустить задачу, печатающую длину переменной → проверить лог/аудит. Ожидаемо: значение подставлено, в логах `***`.

### E2E-8. Перенос

`transfer_tasks(export)` → очистить тестовую БД → `transfer_tasks(import)` → `list_tasks` → `run_task_now`. Ожидаемо: все задачи восстановлены и запускаются.

### E2E-9. Узкое место: полный прогон при высокой нагрузке

Создать 50 задач с разными триггерами → запустить все одновременно → проверить, что не было потерь, блокировок или «вечных running». Ожидаемо: все задачи отработали или отданы в DLQ с понятной причиной.

### E2E-10. Обратная связь: report_bug

Собрать отчёт через `report_bug` с `includeLogs:true`, `includeAnalytics:true`, `dryRun:true` → проверить payload и редакцию секретов → отправить с `destination:"author"` → проверить, что при недоступном приёмнике отчёт ушёл в outbox и задача не заблокировалась. ## 9. Модель выполнения: агент параллельно с человеком

Принцип: **каждая функция проверяется двумя дорожками** — агентом через MCP и пользователем через GUI/дашборд/TUI. Если пользователь не хочет или не может выполнить шаг вручную, агент выполняет его от его имени, и результат должен быть идентичным.

| Дорожка | Кто выполняет | Инструмент | Что проверяется |
|---|---|---|---|
| Агент | MCP-агент | 34 инструмента из Приложения B | Все инструменты вызываются, схемы валидируют аргументы, ошибки структурированы |
| Пользователь | Человек | GUI OpenCode, веб-дашборд, TUI | Кнопки, настройки, формы, дашборд — работают и дают тот же результат |
| Паритет | Агент + человек параллельно | Любая операция (create → run → read → delete) | Состояние совпадает во всех интерфейсах, аудит содержит корректный actor |

**Правило:** после завершения любой задачи (создание задачи, изменение настроек, запуск матрицы, тест триажа и т.д.) агент и человек сверяют результат: `list_tasks` (агент) = таблица GUI = дашборд. Если расходятся — дефект.

## 10. Отчёт об улучшениях продукта после завершения задачи

После завершения каждой задачи (детали Dxx, подзадачи Sxx.y.z или сквозного сценария E2E-N) составляется краткий отчёт: что работает, что нет, и **как можно улучшить продукт**.

### Шаблон отчёта

| Поле | Заполнение |
|---|---|
| Задача | ID и название (например, `S09.2.3 — test manage_local_ai`) |
| Статус | ✅ пройдено / ⚠️ пройдено с оговорками / ❌ не пройдено |
| Что работает | Кратко, какие функции подтверждены |
| Что не работает / ограничения | Дефекты, недоработки, известные пробелы |
| Как улучшить продукт | Конкретные предложения: новый инструмент, исправление UI, документация, тест, оптимизация |
| Приоритет | Высокий / Средний / Низкий |
| Ответственный | Агент / Человек / Оба |

### Пример заполнения

| Поле | Значение |
|---|---|
| Задача | S09.2.4 — Fail-open при недоступности Ollama |
| Статус | ✅ пройдено |
| Что работает | Триаж переходит на правила, уведомления не блокируются |
| Что не работает | Нет уведомления в GUI о том, что Ollama недоступна |
| Как улучшить продукт | Добавить индикатор статуса Ollama в блок триажа (зелёный/красный), тост при переключении на fail-open |
| Приоритет | Средний |
| Ответственный | Агент |

Все отчёты собираются в файл `test-run.log` и прилагаются к итоговому акту приёмки спринта.
