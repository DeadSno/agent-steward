## C1. Ротация reuse-сессии

**Отчёт.** Исправлена поломка ротации: раньше `rotateSessionIfNeeded` удалял сессию и записывал `sessionId: undefined`, а сгенерированная оболочка продолжала передавать удалённый `ses_...`; следующая ротация не могла удалить сессию без ID.

Что сделано:
- `src/core/session.ts`: добавлены `sessionStatePath(taskName)` и `writeSessionStateFile(taskName, sessionId)` — sidecar-файл `<wrapper>.session` рядом с оболочкой. При ротации генерируется новый `sessionId`, старая сессия удаляется, в БД сохраняется новый ID, sidecar перезаписывается.
- `src/index.ts`: при регистрации задачи sidecar обновляется (`writeSessionStateFile(name, effectiveSessionId)`), путь передаётся в обе оболочки.
- `src/core/ps-wrapper.ts`: PowerShell-обёртка принимает `-SessionFile` и читает актуальный ID из файла перед запуском; при ошибке чтения пишет в лог и продолжает без `--session`.
- `src/core/wrappers/bash.ts`: bash-обёртка экспортирует `SESSION_FILE` и в режиме `reuse` читает первую строку файла; пустой ID → запуск без `--session`.

Итог: после ротации оболочка использует новый ID, а не удалённый; повторные ротации снова могут удалять сессию.

## C2. `get_history` игнорировал историю старше 200 запусков

**Отчёт.** Фильтрация перенесена с JS на уровень SQLite.

Что сделано:
- `src/db/history-repo.ts`: `getHistory(taskName?, limit = 200, status?)` строит динамический `WHERE`: задача — `lower(task_name) = lower(?)`, статус — с учётом маппинга `running → error`.
- `src/history.ts`: `loadHistory(taskName?, limit = 200, status?)` прокидывает фильтры в репозиторий.
- `src/index.ts`: агентский `getHistory` и RPC `get_history` вызывают `loadHistory(filter, limit, status)` без фильтрации в памяти и без жёсткого лимита 200.

Итог: запрос истории конкретной задачи возвращает её записи независимо от того, входила ли она в последние 200 глобальных запусков.

## C3. `schedule-gate` разрешал запуск вне окна при `nextOpenAt = null`

**Отчёт.** В `src/core/schedule-gate.ts` ветка «время открытия окна неизвестно» теперь возвращает `3` (skip) вместо `0` (разрешить). При наличии `nextOpenAt` поведение прежнее: `wait > 0` → ожидание/откладывание, `wait <= 0` → запуск.

Итог: задача вне окна без вычисленного `nextOpenAt` больше не запускается ошибочно.

## C4. `candidatesOnDay`: `notBefore` игнорировался без `notAfter`

**Отчёт.** В `src/core/schedule-v2.ts` условие `if (notBefore && notAfter)` заменено на независимую проверку `if (notBefore)`. Нижняя граница окна применяется всегда, верхняя — только если задана.

Итог: хелпер корректен при любых комбинациях границ, а не только когда заданы обе.

## C5. `sessionMaxRuns`: `0` нельзя было передать, хотя документация разрешает

**Отчёт.** Валидация приведена к документации «Unset/0 — no limit».

Что сделано:
- `src/index.ts`: обе Zod-схемы (create/update) — `.min(0)`; обе ручные проверки — `< 0`.
- `src/task-transfer.ts`: импорт принимает `raw >= 0`, текст ошибки — «≥ 0 (0 — без ограничения)».

Итог: явный `0` снимает лимит; отрицательные значения по-прежнему отклоняются.

## M5. `update_task` не обновлял зависимости при смене регистра имени

**Отчёт.** В `src/index.ts` после успешного обновления задачи, если каноническое имя изменилось (`previous.name !== name`), выполняется проход по всем задачам: ссылки в `dependsOn`, `nextTaskOnSuccess`, `nextTaskOnError`, совпадающие со старым именем без учёта регистра, заменяются на новое. Изменённые задачи сохраняются.

Итог: `MyTask → mytask` не оставляет «висячих» ссылок в графе зависимостей.
