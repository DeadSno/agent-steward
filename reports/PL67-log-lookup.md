# PL-67 — поиск лога задачи по короткому/префиксному имени

- Задача: закрыть находку PL-67 из `ROADMAP.md` — `get_task_logs` должен находить лог по короткому имени так же, как по полному.
- Репозиторий: `opencode-windows-scheduler`, ветка `dev`, стартовый HEAD `199b330`.
- Дата прогона: 2026-11-23.
- Коммит и пуш НЕ выполнялись: изменения оставлены в рабочем дереве для post-flight обёртки.
- Чужие файлы, присутствовавшие в дереве до начала (`docs/QA-A2-GUI-TUI.md`, `reports/QA-A2-alert.md`, `reports/QA-A2-final.md`, `reports/QA-A2.7-verify-os.md`), не трогались. Строка PL-68 в `ROADMAP.md` не трогалась.

## Воспроизведение (до правки)

Временный скрипт `%TEMP%\opencode\pl67-repro.mjs` (в репозиторий не добавлялся): выставлял
`OPENCODE_SCHEDULER_HOME` во временную директорию, создавал файл
`<LOG_DIR>/arch-7-approval-queue.log` с содержимым
`[agent-steward] === Run started 2026-11-23\nPL67-MARKER` и вызывал `getTaskLogs` с тремя именами.
Сборка — `dist/` от HEAD `199b330`.

Фактический вывод до правки:

```
SHORT: {"logs":"","error":"Лог задачи \"ARCH-7\" не найден по пути C:\\Users\\...\\home\\logs\\arch-7.log (задача ещё не запускалась)."}
FULL : {"logs":"[agent-steward] === Run started 2026-11-23\nPL67-MARKER"}
MISS : {"logs":"","error":"Лог задачи \"totally-unknown-task\" не найден по пути C:\\Users\\...\\home\\logs\\totally-unknown-task.log (задача ещё не запускалась)."}
```

То есть воспроизведено ровно то, что описано в находке: короткое имя падает, полное работает,
отсутствующий лог даёт понятную ошибку.

Тот же скрипт после правки и `npm run build`:

```
SHORT: {"logs":"[agent-steward] === Run started 2026-11-23\nPL67-MARKER"}
FULL : {"logs":"[agent-steward] === Run started 2026-11-23\nPL67-MARKER"}
MISS : {"logs":"","error":"Лог задачи \"totally-unknown-task\" не найден по пути C:\\Users\\...\\home\\logs\\totally-unknown-task.log (задача ещё не запускалась)."}
```

## Причина

`getTaskLogs()` в `src/core/scheduler/logs.ts` строил путь только как
`path.join(LOG_DIR, sanitizeName(name) + '.log')`. Для `ARCH-7` это `arch-7.log`, тогда как
обёртка пишет лог под нормализованным полным именем задачи — `arch-7-approval-queue.log`.
Слаг/полное имя задачи по её записи в реестре никогда не резолвился; поиск по шаблону в
`LOG_DIR` отсутствовал.

## Решение

В `src/core/scheduler/logs.ts` добавлен резолвер пути к логу с фиксированным приоритетом:

1. прямой файл `<slug>.log` — текущее поведение полных имён сохраняется;
2. запись задачи из реестра (`listTasks()` из `src/db/tasks-repo.js`): имя запроса и полное имя
   задачи сравниваются через `sanitizeName()` (регистронезависимо, пробелы/дефисы/спецсимволы
   сведены к одному «-»), короткое имя считается префиксом полного; если у совпавшей задачи есть
   файл — берём его (`ARCH-7` → `ARCH-7 - Approval queue` → `arch-7-approval-queue.log`);
3. если реестр недоступен (`node:sqlite` отсутствует/БД не открылась) или подходящей записи нет —
   поиск файлов `<slug>*.log` в `LOG_DIR`;
4. при нескольких кандидатах — приоритет у задачи из реестра, иначе самый короткий slug
   (ближе к запросу), затем лексикографический порядок. Выбор детерминирован.

Ошибки чтения БД подавляются и переводят резолвер в файловый fallback: доступ к логам не должен
зависеть от состояния реестра. Публичный контракт `Promise<{logs, error?}>` и текст ошибки
«Лог задачи "..." не найден по пути ... (задача ещё не запускалась).» не изменены.

Зависимость от реестра добавлена только как `import { listTasks } from "../../db/tasks-repo.js"`
(заметка: `getDb()` ленивый, импорт не открывает БД на загрузке модуля). Другие модули реестра не менялись.

## Урок оркестрации: регистрация новой сюиты

Промпт задачи требовал создать новый `test-task-*.mjs`, но не включал в SCOPE файлы регистрации.
Мета-гейты `test-docs.mjs` и `test-test-plan.mjs` корректно поймали это: каждый файл `test-*.mjs`
должен быть упомянут в скриптах `package.json` и в `TEST-PLAN.md` §5, а счётчики шапки должны
совпадать с фактом. Оркестратор расширил SCOPE и зарегистрировал сюиту до коммита; требование
добавлено в `skills/scheduled-job-best-practices/SKILL.md`, чтобы агенты не повторяли эту ошибку.

Отдельно исправлен конфликт ID в `ROADMAP.md`: два разных бага получили одинаковые номера
PL-68/PL-69 (один — от параллельного агента, другой — от этой сессии). Находки этой сессии
перенумерованы в PL-83/PL-84; старые записи PL-68/PL-69 от parallel agent не тронуты.
