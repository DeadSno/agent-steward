# CONCEPT — Верифицируемая локально-первая оркестрация агент-задач

> Статус: north star проекта **agent-steward**. Любое решение по фиче сверяется с ним.
> Система гибридная: миссии по триггеру **или ad-hoc**, на усмотрение пользователя.

## TL;DR

Локальные модели слабы в открытом творчестве, но компетентны в ограниченной,
проверяемой работе. Объективная проверка дёшева и надёжна. Поэтому: дешёвая
локальная модель пытается сделать **максимум проверяемой работы**; объективный
гейт решает, принято или эскалировать в дорогое облако; каждый исход учит
систему — роутинг точнее, локальные модели способнее именно под твои задачи.
Со временем локальный сетап становится личной, приватной, дешёвой и всё более
умной рабочей силой.

Это и есть продукт. Всё остальное — обвязка, включая планировщик.

---

## 1. Проблема

Разработчику, который хочет автономной agent-работы, сегодня доступны три
плохих варианта:

1. **Не автоматизировать** — рутина остаётся ручной.
2. **Автоматизировать в облаке** — токены на каждый прогон, код уходит наружу,
   нет контроля над тем, что исполняется и куда течёт.
3. **Автоматизировать локально наивно** — слабая модель молча выдаёт брак,
   падает, двоится; доверия нет, затею бросают.

Корень всех трёх: **нет слоя, который делает агент-труд одновременно дешёвым,
приватным и проверяемо надёжным.**

- OpenCode даёт агентов, но не даёт супервизии: capability-роутинга, объективных
  гейтов, честной экономии, learning-loop.
- Облачные оркестраторы дают масштаб, но не приватность и не локальную экономию.
- Swarm-фреймворки дают коллаборацию, но не надёжность и не экономию.
- Планировщики дают расписание, но не верификацию и не контроль ущерба.

Ниша пуста: **локально-первая, верифицируемая, компаундящаяся оркестрация**.

## 2. Ключевой инсайт

Слабость локальных моделей — не приговор, а ограничение, обходимое архитектурой:

- Локаль тянет **ограниченные, хорошо scaffolding-нутые, объективно проверяемые**
  задачи. Это и есть масса реальной рутины.
- **Объективный гейт** (тесты / линт / схема / diff-applies / команда) дёшев и
  не врёт. Он позволяет натравливать локаль на максимум задач: брак ловится и
  эскалируется, а не уезжает в прод.
- Исходы гейта — **бесплатная разметка**: они учат роутинг и копят gate-passed
  датасет для прокачки весов.

Проверка — не надзор, а **двигатель экономики и обучения**.

## 3. Что это такое

**Фреймворк-супервизор поверх OpenCode**: локальный control plane, который
принимает миссии — **ad-hoc по желанию пользователя или по триггеру/расписанию** —
раскладывает их на шаги с ролями, назначает каждый шаг **самому дешёвому способному
исполнителю** (локаль → облако только при провале гейта), объективно верифицирует
результат, честно считает экономию и компаундится.

Метафора: бригадир смешанной бригады. Дешёвые локальные подмастерья делают
ограниченную работу под инспекцией; дорогие облачные специалисты вызываются,
только когда инспекция завалила подмастерье; каждая инспекция делает
подмастерьев лучше именно в твоих ремёслах.

Бригадира можно позвать руками в любой момент — он не живёт внутри календаря.

## 4. Цель и критерии приёмки (north star)

Четыре столпа — **Надёжно, Приватно, Дёшево, Компаундится** (таблица ниже).
Это независимый список свойств системы, а не формула приоритетов.

Формула приоритетов при конфликте — другая вещь:
**надёжно > приватно > дёшево > краткосрочные фичи**. Её последний член —
**не четвёртый столп**: это то, чем жертвуют в первую очередь. Четвёртый
столп «Компаундится» не противопоставлен «краткосрочным фичам», а накапливается
за счёт того, что краткосрочные фичи откладываются. `explore` — управляемая
инвестиция «дёшево-сегодня» в «компаунд-завтра».

| Столп | Что значит | Метрика |
|---|---|---|
| **Надёжно** | ноль тихих отказов / двойных прогонов / fake-done / порчи репо | trust-инциденты = 0; гейт независим и tamper-evident; полнота аудита |
| **Приватно** | control plane, данные, аудит, triage локальны | % инференса/данных локально; cloud-egress только explicit и залогирован |
| **Дёшево** | локаль закрывает максимум gate-able задач | net-экономия (минус верификация/эскалации/overhead), local share, escalation rate |
| **Компаундится** | success rate и экономия растут под пользователя | тренд local success_rate и first_pass_rate ↑, eval-lift адаптеров, рост scaffolding |

Цель одним предложением: **разработчик оставляет AI-агентам свою рутину —
дёшево, приватно, надёжно, когда сам захочет или по расписанию — и его локальный
сетап с каждой неделей работает лучше и дешевле именно под его задачи.**

## 5. Способности (что он делает)

- **Миссия** = цель + scope + явный критерий приёмки (гейт). Без критерия —
  не миссия, а лотерея.
- **Гибридные входы**: ad-hoc (инструмент/CLI/GUI/RPC), внутренние (цепочка, DAG,
  retry, эскалация), registered (cron, once, file, git, mcp-event, webhook).
  Регистрация в планировщике ОС **опциональна**.
- **Декомпозиция** на шаги/роли (planner → implementer → reviewer …).
- **Capability-aware роутинг (3 слоя)**:
  - **Слой 1 — статические правила (0 токенов, мгновенно):**
    ```json
    {
      "read_file": { "transport": "direct", "executor": "local" },
      "write_file": { "transport": "direct", "executor": "local" },
      "run_tests": { "transport": "direct", "executor": "local" },
      "apply_diff": { "transport": "direct", "executor": "local" },
      "github_create_pr": { "transport": "mcp", "executor": "local" },
      "jira_update_task": { "transport": "mcp", "executor": "cloud" }
    }
    ```
  - **Слой 2 — Capability Map (0 токенов):** SQLite `task_type → model /
    success_rate / first_pass_rate / avg_attempts / avg_cost / avg_time /
    last_10_runs`. Обучается на исходах гейта, с затуханием старых данных.
    Высокая надёжность → локаль; низкая → облако или ревью.
  - **Слой 3 — локальная модель (только декомпозиция и неоднозначность):**
    модель не маршрутизирует каждый шаг.
  - **Эскалация при провале гейта — по правилу, без участия модели.**
- **Reliability вместо бинарного исхода**: «прошло с первой попытки» ≠ «с третьей»;
  first_pass_rate и среднее число попыток участвуют в роутинге.
- **Объективная верификация** (keystone): провал → эскалация / ретрай / откат;
  никогда «готово» на слово агента. Гейт **всегда hard**.
- **Целостность гейта**: gate-файлы и команда вне write-scope агента; snapshot и
  хэш gate-входов и политики фиксируются на старте и сверяются перед вердиктом.
  Flake/infra-исходы не обучают карту. Shadow/canary — для маршрутов и адаптеров,
  не для приёмки артефакта.
- **Отложенные внешние эффекты**: до гейта агент заявляет намерения
  (`effect_intents`), а не выполняет irreversible-действия. Применение — только
  после pass; при провале — отброс или компенсация.
- **Контракт безопасности миссии**: класс риска компилируется в исполняемую
  политику (allow/deny, egress, обязательные гейты, бюджет) **до** исполнения.
- **Честная экономика**: savings ledger (net-контрфактика с учётом эскалаций,
  верификации и overhead), токены/стоимость по шагам и моделям.
- **Полный аудит**: кто, каким инструментом, какой файл, когда, почему
  эскалировали. Ledger — tamper-evident (хеш-цепочка), не граница безопасности.
- **Learning-loop**: capability-карта → scaffolding/few-shot из успешных решений →
  eval-harness → shadow → canary → (staged) LoRA на gate-passed датасете.
- **Автономность по выбору**: ad-hoc или расписание; переживает ребут; не двоится;
  не зависает; leases/locks/таймауты/бюджеты.

## 6. Исполнительный цикл (его задачи)

1. Принять миссию: цель + scope + gate-спека + **контракт безопасности**;
   скомпилировать политику (класс риска → allow/deny + egress + обязательные
   гейты + бюджет); approval, если класс риска требует.
2. Разложить на шаги, назначить роли (локальная модель — только здесь).
3. **Роутинг шага**: статические правила → capability-карта с учётом reliability
   (first_pass_rate, попытки, decay), локаль first, explore capped.
4. **Context compilation**: собрать бандл под окно выбранной модели и бюджет
   токенов — scaffolding/few-shot из ledger + repo-map. Пересборка при эскалации.
5. Выполнить шаг: capability issuance на шаг (TTL), least privilege,
   worktree/sandbox; внешние эффекты — только намерения.
6. Прогнать **hard, независимый, tamper-evident, flake-aware** гейт.
   - Pass → применить намерения → ledger (экономия + пример + provenance) → обновить карту.
   - Fail → эскалация / ретрай / откат в рамках живого бюджета; эскалация возвращает к шагу 3.
7. Собрать артефакт миссии (diff/PR из worktree, отчёт, аудит-трейл).
8. Отчитаться честно: net-экономия, success rate, first_pass_rate, escalation rate,
   overhead.
9. Обновить роутинг/eval; периодически — дообучить адаптер (staged, opt-in).

Шаги 3–6 — внутренний цикл на каждый шаг миссии.
Сквозные слои: телеметрия (span на шаг), живой бюджет, аудит, durable state.
Human review / approval — **тип гейта**, доступен на любом шаге; пауза не потребляет compute.

## 7. Архитектура (слои)

```
[ ВХОДЫ-АДАПТЕРЫ ]
  ad-hoc:      run_mission / CLI / GUI / RPC        ← без регистрации в ОС
  внутренние:  chain / DAG / retry / escalation     ← без регистрации в ОС
  registered:  cron / once / file / git / mcp / webhook
        │
        ▼
[ MISSION RUNTIME — ядро ]
  intake: цель + scope + gate-спека + safety → компиляция политики + бюджет
        │
  createRun (durable, trigger_kind)
        │
  planner: декомпозиция на шаги/роли
        │
  router: capability-карта + reliability → локаль first; explore capped
        │        │ эскалация → возврат к router
        │        ▼
        │   [ облачные модели (fallback) ]
        ▼
  context compilation: окно модели + бюджет токенов (scaffolding + repo-map)
        │
  executor: OpenCode-агенты, capability issuance (TTL), worktree/sandbox
            внешние эффекты → intents (не применяются)
        │
  GATE: hard, независимый, tamper-evident, flake-aware   ← keystone
        │ pass                          │ fail
        ▼                               ▼
  применить intents → ledger      escalate / retry / rollback
        │
  learning: карта → scaffolding → eval → shadow/canary → LoRA (staged)
        │
  control plane: локальный, приватный, аудит, dashboard

[ РЕГИСТРАЦИЯ ТРИГГЕРА — опционально ]
  Task Scheduler / crontab / launchd — только для registered-входа
```

Объекты: **миссия** — единица работы; **задача** — миссия-шаблон + триггер
(опциональна); **запуск** — durable-исполнение миссии.

Локально-первым является **control plane и роутинг**; инференс — гибрид.
Приватность = данные/аудит/управление локальны, а не «ни одного облачного токена».

## 8. Границы (чем НЕ является)

- Не open-ended AGI-swarm: миссии ограниченные, с явным критерием приёмки.
- Не замена способной облачной модели на сложном: облако — эскалация.
- Не отмена человеческого ревью критичного: гейт поднимает пол, не потолок.
- Не облачный SaaS и не multi-machine: локальный control plane, одна машина.
- Не «плагин-планировщик»: scheduler/уведомления/аналитика — триггеры и обвязка.
- **Не «только планировщик»**: ad-hoc миссия без расписания — полноправный вход.
  Регистрация в планировщике ОС опциональна; его недоступность не блокирует ядро.

## 9. Душа: flywheel

Больше задач → больше локальных попыток → больше исходов гейта → точнее
capability-карта и больше примеров → **примеры инжектятся в контекст** → выше
local first_pass_rate → больше экономия и сильнее адаптеры → ещё больше задач
выгодно гнать через локаль.

Ключевое звено: примеры не просто копятся, а **используются** (context compilation).
Без него flywheel не крутится.

## 10. Реальность железа (ограничение, учтённое в дизайне)

Целевая стартовая конфигурация — потребительская (пример: RTX 3050 8 ГБ,
16 ГБ RAM). Отсюда:
- инференс локально: QLoRA/квант 3–8B;
- обучение: только QLoRA 3–4B, low-rank, накопленным gate-passed датасетом,
  пакетами, а не онлайн;
- прокачка staged: сначала scaffolding/роутинг (дёшево, сразу), веса — когда
  датасет и железо позволяют;
- context compilation обязателен: малое окно — не повод отказываться от задачи.

LP-1.1/1.2 фиксируют критерии датасета и обязательный офлайн-eval: репозиторий
хранит версионированный снимок и символическую ссылку на веса внешнего пайплайна.
Онлайн-обучение запрещено на уровне формата; включение адаптера возможно только
после сравнения метрик с ранее зафиксированным эталоном.

Дизайн не зависит от конкретного железа: capability-карта и гейты работают и на
слабой, и на сильной локали; меняется лишь доля задач, которую тянет локаль.

## 11. Как поймём, что пришли (definition of done концепции)

Вертикальный срез работает end-to-end и измеримо:

1. **ad-hoc** миссия с явным гейтом и safety-контрактом принята, политика
   скомпилирована, миссия разложена — **без регистрации в планировщике ОС**;
2. шаги смаршрутированы локаль-first по capability-карте с учётом reliability;
3. гейт объективно верифицировал; провал экалировался/откатился без тихих
   отказов; irreversible не произошёл до pass;
4. ledger показал честную net-экономию и escalation rate;
5. learning-loop обновил capability-карту, положил пример и **переиспользовал** его;
6. паритет: та же спека через registered-вход даёт тот же маршрут и вердикт;
7. на фикс-наборе задач за N недель: local success_rate и first_pass_rate ↑,
   net-экономия ↑ при неизменном качестве (eval не деградировал).

Когда 1–7 воспроизводимо — концепция достигнута; всё дальнейшее = масштаб.

## 12. Открытые вопросы / риски (честно)

- Качество локального вердикта на пограничных задачах → правила/пороги и
  shadow-режим, а не слепая вера модели.
- Cost of verification → учитывать в net-экономике, кэшировать.
- Explore может тратить впустую → capped explore-бюджет, bandit по типам задач.
- Датасет для весов копится медленно → staged-прокачка, не обещать онлайн-LoRA.
  LP-1.2 добавляет офлайн-кандидата (`buildLoraAdapterCandidate`,
  `evaluateLoraAdapter`, `promoteLoraAdapter`): падение success_rate или
  first_pass_rate более чем на 0.02 либо net-экономии более чем на 1 USD
  блокирует включение. Веса создаёт внешний пайплайн, репозиторий хранит только
  ссылку и решения гейта.
- LP-1.3 добавляет теневой режим: включение фиксируется записью с нулевой долей
  трафика (`LORA_SHADOW_TRAFFIC_SHARE`), выход в канареечный режим с долей 5%
  требует сравнения метрик с эталоном, откат обнуляет обе доли и возвращает
  снимок эталона. По измеренному снимку от 25.11.2026 (183 строки, 122 кейса,
  success_rate 0.2593, first_pass_rate 0.4208, net 2.5829 USD) полный трафик не
  включался: прокачка остаётся staged, онлайн-обучение запрещено.
- Prompt-injection даже при гейте → гейт + аудит + allowedTools как пол;
  внешний контент недоверенный по умолчанию; критичное — человеку.
- **Reward hacking**: агент правит тесты/гейт → при создании задачи
  `src/core/gate-integrity.ts` фиксирует snapshot входов гейта (команда/файл
  хука, prompt, таймаут) в `PLUGIN_DIR/gate-snapshots/` с SHA-256; обе обёртки
  проверяют хэш непосредственно перед запуском гейта. Расхождение или отсутствие
  snapshot → fail-closed: гейт не выполняется, запуск считается ошибкой.
  Обязательная тест-атака (подмена gate-команды/хука) есть в `npm test` и в CI
  на Windows, macOS и Linux. Мера защищает **определение гейта**, а не исходники
  репозитория, которые гейт проверяет: подмена самих тестов агентом эту проверку
  не обходит, но и не детектируется ею. Права вне write-scope остаются планом;
  `gate_outcomes` с хэш-цепочкой уже реализованы (ARCH-1.2/1.3: `prev_hash` +
  `row_hash`, `verifyGateOutcomeChain()`), это tamper-evident аудит, а не граница
  безопасности. Status: 🔄 (базовая мера + ledger-цепочка).
- **Irreversible до вердикта** → отложенные эффекты (intents) и компенсация.
- **Хеш-цепочка ledger** — tamper-evident аудит, **не** граница безопасности;
  граница — права и изоляция.
- **Зависимости под гипотезы** → сначала переиспользуем существующее; новый
  движок/БД только с доказанной необходимостью.

## 13. Стратегия развития: от плагина к фреймворку

### 13.1 Локальный интеллект

Максимум проверяемой работы на локальных моделях с компандингом. Объективный
гейт дёшев и не врёт, поэтому локаль направляется на максимум задач: брак
ловится и эскалируется. Исходы гейта — бесплатная разметка.

### 13.2 Мультиагентная оркестрация

Ролевая декомпозиция миссий на шаги. Каждый шаг — самому дешёвому способному
исполнителю; облако только при провале гейта.

### 13.3 Непрерывное улучшение Control Plane

Существующий функционал (планировщик, DAG, матрицы, Quality Gates, GUI, аудит) —
фундамент доверия, а не отдельный продукт. Дорабатывается наравне с ядром.

### 13.4 Путь к универсальности

- **Этап 1 (текущий):** глубокая интеграция с OpenCode V1 и V2 — один пакет,
  dual export, общее ядро.
- **Этап 2:** выделение mission runtime, независимого от планировщика ОС, и
  абстракция слоя исполнения (Agent Executor Interface).
- **Этап 3:** универсальный фреймворк оркестрации, совместимый с любым агентом
  через MCP или стандартные API; интероперабельность — через стабильные форматы
  (pipeline YAML, SQLite ledger) и MCP, а не через соответствие чужим схемам слоёв.

## 14. Продукт для людей (не на продажу)

- **Суверенитет пользователя.** Данные локальны и экспортируемы; роутинг
  переопределяем; обучение отключаемо; без аккаунтов, SaaS и телеметрии.
- **Свобода сценария.** Можно жить без расписаний, можно на расписаниях, можно
  смешивать. Одноразовая работа не требует регистрации задачи.
- **Честность.** «Сэкономлено $» — консервативная оценка с методикой рядом;
  метрики воспроизводимы из ledger. Термин — tamper-evident, не tamper-proof.
- **Низкий порог.** Работает на скромном железе, безопасно по умолчанию,
  понятные дефолты, документация на нескольких языках.
- **Долговечность.** Скучные технологии, мало зависимостей, стабильные форматы,
  дисциплина миграций: через годы оно всё ещё запускается.
- **Открытость.** Открытые форматы pipeline и ledger, библиотека рецептов,
  skill-экосистема — сообщество расширяет без maintainer'а.
- **Пол, не потолок.** Гейт и approval поднимают минимальную планку качества и
  безопасности; критичные решения остаются за человеком.
