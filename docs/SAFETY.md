# SAFETY — контракт безопасности миссии

> Шаг 1 цикла v2.1. Принцип: **продукт для людей** — не сломать репо, не слить
> данные, не разорить. Порядок столпов: надёжно > приватно > дёшево > фичи.
> Контракт одинаков для **ad-hoc**, внутренних и registered запусков.

## 1. Классы риска

| Класс | Что делает | Примеры | Default |
|-------|-----------|---------|---------|
| **R0** read-only | Читает, ничего не меняет | анализ, отчёт, обзор | разрешён |
| **R1** local-write | Меняет файлы в изолированном worktree | правка кода, бойлерплейт | разрешён в worktree |
| **R2** external-effect | Меняет внешнее состояние | git push, PR, API-запись, деплой | **approval + отложенные эффекты** |
| **R3** destructive / egress | Удаляет, льёт данные наружу | reset --hard, удаление, отправка наружу | **approval + явный opt-in** |

Класс определяется по **инструментам и командам**, а не по описанию миссии.

## 2. Компиляция политики (принуждение, не декларация)

```
risk R2 → allowedTools:  [read, edit, glob, grep]
          deniedTools:   [shell]
          egress:        [] (кроме явного allowlist)
          requiredGates: [tests, lint, approval]
          effects:       deferred (intents)
          budget:        из контракта
```

- Enforcement — существующие `permissions` / `OPENCODE_CONFIG_CONTENT` +
  egress-контроль на уровне исполнения.
- `policy_hash` пишется в ledger; изменение политики посреди миссии → `fail` +
  аудит-инцидент.
- Внешние policy-движки (OPA/Cedar) на этом этапе не используем: локальная одна
  машина, мало зависимостей.

## 3. Capability issuance на шаг

- Агент получает **scoped-конфиг ровно на шаг**, не на миссию.
- Секреты — короткоживущая инъекция только используемых (`collectSecretNames`),
  очистка после шага.
- Никаких долгоживущих токенов в окружении задачи.

## 4. Уровни изоляции

| Уровень | Механизм | Когда |
|---------|----------|-------|
| 1 (opt-in: `worktree: true`) | git worktree | R0/R1, когда включено у задачи |
| 2 | OS-jail: ограничение ФС/процессов | R1 с недоверенным контентом |
| 3 | Docker runner (opt-in, спринт 46) | R2/R3, недоверенные зависимости |

**Worktree не защищает от сети/API/БД** — поэтому обязателен следующий раздел.

## 5. Отложенные внешние эффекты

1. До гейта агент **не выполняет** irreversible-действие, а пишет `effect_intents`.
2. Гейт проверяет артефакт и валидность intents (политика, egress, blast-radius).
3. `pass` → применение, отметка `effects_applied_at`.
4. `fail` → discard; частично применённые — компенсация (saga).

Так «локальность» действительно ограничивает ущерб, а не только конфликты файлов.

## 6. Blast-radius

- Работа в worktree; основное дерево не трогается до принятия.
- Одноразовый worktree удаляется после прогона; остатки старше суток выметаются,
  sidecar без рабочей копии очищается, чужие каталоги и свежие запуски не трогаются.
- Запрет push в защищённые ветки; лимит числа файлов и объёма diff.
- Opt-in guards (W-3): shell-`command` и/или `semantic`-условия (`filesExist`/
  `filesMissing`, `branch` glob, `changedPaths` в `changedSince..HEAD`); любая
  ошибка или невыполненное условие — запуск пропущен (fail-closed), видимый
  статус `skipped` — в W-4.
- Egress только по явному allowlist; всё в аудит.
- Destructive-команды запрещены без явного разрешения в контракте.

## 7. Бюджет миссии (живой)

```yaml
budget:
  maxUsd: 0.50
  maxTokens: 200000
  maxMinutes: 30
  maxEscalations: 2
```

Счётчик ведётся в durable-run и учитывает **верификацию и эскалации**. При
подходе к границе роутинг предлагает более дешёвую модель или `review`;
превышение → circuit-breaker, статус `review`, уведомление.

## 8. Approval-матрица

| Условие | Требуется |
|---------|-----------|
| R0 / R1 в worktree | нет |
| R2 (внешний эффект) | approval + отложенные эффекты |
| R3 (destructive / egress) | approval + явный opt-in |
| Превышен бюджет | остановка + review |
| Capability-карта даёт `review` | очередь человеку с evidence |

`approval` — **тип гейта**. Исполнение — на существующей паузе с инъекциями:
paused-миссия **не потребляет compute**, комментарий человека доставляется шагу
при resume.

## 9. Least privilege и недоверенный контент

- Политика прав задачи (`hybrid` по умолчанию) — пол, не потолок.
- Gate-файлы и gate-команда вне write-scope агента.
- Внешний контент (web, issues, PR) — недоверенный по умолчанию: prompt-injection
  учитывается как угроза.
- Секреты маскируются в логах, истории и аудите.

## 10. Kill switch

- Остановка миссии в любой момент; откат worktree чистый, intents отбрасываются.
- Глобальная пауза планировщика останавливает новые **registered** запуски;
  ad-hoc миссии можно запускать и на паузе планировщика (это разные подсистемы).

## 11. Ad-hoc миссии (AB-8)

Ad-hoc запуск (`run_mission`, CLI `agent-steward run`, GUI, RPC) строит тот же
`RunContext`, что и registered-задача: политика `hybrid` по умолчанию,
`allowedTools` / `deniedTools`, Quality Gate и таймаут передаются в обёртку,
а результат пишется в `runs` / `run_steps` с `metadata.adHoc = true`. Записи в
Task Scheduler, launchd или crontab не создаются. Один workspace — одна
активная миссия: параллельный запуск в том же каталоге отклоняется. `dryRun`
показывает план и маршрут, не создавая run.

## 12. Инварианты (проверяются тестами)

1. Миссия без gate-спеки не принимается.
2. Миссия без safety-контракта получает safe-default (R1, worktree, бюджет).
3. R2/R3 без approval не стартует.
4. Агент не получает инструмент, запрещённый скомпилированной политикой.
5. Агент не может изменить gate-файлы (`gate_hash` сверяется).
6. Irreversible-действие невозможно до `pass`.
7. Превышение бюджета останавливает миссию.
8. Каждый вердикт, эскалация и применение эффектов попадают в аудит.
9. **Ad-hoc миссия проходит ту же политику, бюджет и gate, что и registered.**
10. **Ad-hoc миссия не создаёт записей в планировщике ОС.**
