# Спайк: structured output локальной модели (30.1)

Дата: 15.11.2026. Статус: **выполнен**.

## Вопрос

Можно ли использовать 4B-модель через Ollama для триажа уведомлений, не полагаясь на «повезёт с JSON»? Нужен ли retry и как валидировать ответ?

## Окружение

- OpenCode **2.2.3**, Ollama **0.40.16**.
- GPU: NVIDIA GeForce RTX 3050, 8 ГБ VRAM; модель загружается целиком.
- Модель: `hf.co/Qwen/Qwen3-4B-GGUF:Q4_K_M` (Qwen3 4.02B, Q4_K_M, 2.5 ГБ).
- Почему не `qwen3:4b`: официальный реестр Ollama отдаёт блобы с Cloudflare R2, а соединение с R2 на этой машине сбрасывается и по IPv4, и по IPv6. Hugging Face доступен, поэтому модель скачана оттуда; для Ollama это тот же GGUF и тот же runner.

## Формат id моделей Ollama в OpenCode V2

- OpenCode сам опрашивает `http://127.0.0.1:11434`, получает список моделей через `/api/tags` и `/api/show` и добавляет их в `/models` без подключения аккаунта.
- Ссылка на модель — **`ollama/<model>`**. Для модели из HF имя будет `ollama/hf.co/Qwen/Qwen3-4B-GGUF:Q4_K_M`.
- Для удалённой Ollama `providers.ollama.settings.baseURL` должен включать `/v1`; опциональный `apiKey` уходит bearer-токеном.
- В инвентарь попадают только модели с capability `completion`; embedding-only модели исключены.
- При недоступности Ollama OpenCode сохраняет последний успешный инвентарь, поэтому «модель есть в списке» не гарантирует, что сервер сейчас жив.

Вывод для планировщика: хранить `ollama/<model>` как обычный id модели, но перед запуском проверять доступность провайдера, а не только наличие id в списке.

## Результаты 10 прогонов

Команда:

```powershell
node scripts/spike-local-structured.mjs `
  --model "hf.co/Qwen/Qwen3-4B-GGUF:Q4_K_M" `
  --runs 10 --timeout 180000 `
  --out docs/spikes/ollama-qwen3-4b.json
```

| Метрика | Значение |
|---|---|
| Валидный JSON | **10/10** |
| Соответствие JSON Schema | **10/10 (100%)** |
| Средняя латентность | **20 336 мс** |
| p95 латентности | **20 927 мс** |
| Разброс | 19 961–20 927 мс |

Первый запрос после загрузки модели занял **41.7 с** (cold start). Последующие — около 20 с.

Ответы во всех прогонах одинаковые: `category=quality`, `severity=high`, `confidence=0.95`. Это ожидаемо при `temperature: 0` и одном и том же сценарии; спайк проверял стабильность формата, а не качество классификации на разнообразных уведомлениях.

## Вывод

1. **Формат надёжен:** Qwen3-4B с `format: <JSON Schema>` выдала схема-валидный JSON 10/10. Retry ради формата не нужен.
2. **Валидацию схемы всё равно оставляем:** `format` — это подсказка, а не гарантия; парсер должен отклонять лишние поля, пустой `reason`, выход за enum и `confidence` вне `0..1`.
3. **Один retry оставляем как страховку** на таймаут/сетевую ошибку, а не на «модель не попала в JSON».
4. **Латентность — главный ограничитель:** 20 с в среднем и 42 с на холодную. Дефолтный `timeoutMs: 15000` из 30.2 для такой модели слишком мал. Для синхронного триажа нужен таймаут не меньше 45–60 с либо асинхронная обработка; иначе fallback на правила будет срабатывать почти всегда.
5. **Fail-open обязателен:** триаж не должен задерживать или блокировать доставку уведомления.
6. **Логировать** модель, версию, латентность и причину fallback, чтобы 30.8 собрал статистику.

## Решение для 30.3–30.5

- Валидировать JSON и схему на стороне планировщика.
- Один retry только при таймауте, обрыве соединения или невалидном JSON; при повторной ошибке — правила.
- Таймаут по умолчанию поднять до **45 000–60 000 мс** (или сделать триаж асинхронным).
- Порог уверенности из 30.2 (`0.6`) применять после валидации схемы.
- Не считать одинаковые ответы на один сценарий доказательством качества классификации.

## Как воспроизвести

```powershell
ollama serve
ollama pull hf.co/Qwen/Qwen3-4B-GGUF:Q4_K_M
node scripts/spike-local-structured.mjs --model "hf.co/Qwen/Qwen3-4B-GGUF:Q4_K_M" --runs 10 --timeout 180000 --out docs/spikes/ollama-qwen3-4b.json
```

Если модели нет, скрипт завершится с кодом 2 и подскажет, что скачать. Если Ollama недоступна — тоже код 2, без ложного «спайк пройден».

- Проверить поведение при длинном уведомлении и при обрезанном контексте.
